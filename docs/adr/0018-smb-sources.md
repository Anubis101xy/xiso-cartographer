# 0018. NAS shared folders over SMB: libsmb2, NT-hash logins, @smb folders, game folders, a scan, PLAY, archives, deleting installs and apps

- **Status:** Accepted (owner of this fork, 2026-10-29)
- **Date:** 2026-10-29

## Context

Many owners keep their images on a NAS, which shares them over SMB: Windows file sharing, which every NAS turns on by default. Until now the console could install from one only if it also ran an HTTP server with `Range` support ([map.md §4.2](../formats/map.md#42-url)), which most NAS systems don't offer for a shared folder without extra setup. The owner of this fork has a TerraMaster F4 and wants to pick a game on the console and have it install from the NAS, then play it, with nothing to do on a PC.

The console has no SMB client of its own: the kernel has none, and each retail game brings its own network code. Running games *from* the NAS without copying them would need a kernel that keeps a network drive alive under the running game, which no app can provide. Installing first, as this app does for every source, needs only a client in the app.

[libsmb2](https://github.com/sahlberg/libsmb2) (LGPL-2.1) is a portable SMB2/3 client in C with NTLMv2, signing, SMB3 encryption and share enumeration, already ported to embedded lwIP systems (the Pico W) and, for the leaked XDK, to the Xbox. nxdk's clang defines `_WIN32` and `_MSC_VER` but has lwIP's BSD sockets, not Winsock.

## Decision

1. **libsmb2, vendored with a small nxdk port.** `third_party/libsmb2` holds upstream commit `727feaa` plus a port that's reviewed as a diff (`third_party/libsmb2/xcat/nxdk.patch`, explained in its README): an `NXDK` platform that uses lwIP's socket API, its `_WIN32` paths turned off for nxdk, the byte order, the few C library functions nxdk lacks, and a hook through which the platform gives it strong random bytes (the console has no generator; it gets ADR 0012's entropy pool). It's built at `-O2` with its own warnings off, like BearSSL. On PCs (Linux, macOS) it's built from the same sources with a `config.h` from its own checks; Windows hosts build without SMB.
2. **The client is platform code, not core.** libsmb2 opens its own sockets, and `core/` never touches files or sockets ([ARCHITECTURE.md §2](../ARCHITECTURE.md#2-layers)). So `platform/smb` (the same sources for the XBE and for `xcat-cli`) wraps it: connect to a share, list shares and folders, list an `@smb` folder, and read a file as an `xc_source`, so installs go through `xc_install` like every other source (xiso, full-disc, zips, resume, verification). What can be parsed without the network stays in core and is tested and fuzzed: `smb://` addresses, image names, the NT hash (with its own MD4), listings, and NetBIOS node status answers ([smb.md](../formats/smb.md)).
3. **Addresses and the map.** `smb://host[:port]/share/path` ([smb.md §1](../formats/smb.md#1-addresses)) is accepted wherever a map entry's URL is, and a new directive `@smb <folder>` ([map.md §5.4](../formats/map.md#54-smb-folder)) generates entries keyed by name from the images in a folder and the folders in it, like `@archiveorg`. Older readers skip the directive with a warning (map.md §5.3), so the map stays v1.
4. **Logins are NT hashes in the credentials file.** A section may hold `smb_user`, `smb_domain` and `smb_nthash` ([credentials.md §4.1](../formats/credentials.md#41-smb-logins)). The console writes it when the user logs in on SETTINGS > NAS; the password is used once to compute the hash and wiped, never stored or logged. The hash still logs in to SMB servers, so the guide asks for a NAS user that can only read the games share. No section means a guest login. HTTP and SMB sections may name the same host (the overlap rule applies per kind, credentials.md §5): one machine can serve both.
5. **Finding the NAS is a scan of the console's own network, nothing more.** TCP 445 on each address of the console's /24 (or smaller) network, 16 at a time, then one NetBIOS node status request to each server that answered, for its name ([smb.md §5](../formats/smb.md#5-finding-the-nas)). No broadcast or multicast: nxdk's lwIP has no IGMP, and a sweep finds servers whatever discovery protocol they run. lwIP's socket table and ARP table are enlarged for it (`MEMP_NUM_NETCONN` 32, `ARP_TABLE_SIZE` 64). An address can always be typed instead.
6. **SETTINGS > NAS** does it all on the console: it shows the console's own address, lists the NASes with a saved login (and those the map uses) first, finds others with a scan or a typed address, logs in (user name and password on the on-screen keyboard, once: the login is saved as soon as the NAS accepts it; no user name is a guest), browses the shares and folders, and adds a folder, the one browsed or the highlighted one (X), as an `@smb` line, then lists the games. (Amended 2026-11-01 after the first hardware run: the login was only kept once a folder was added, and the menus were unclear about which folder was meant.)
7. **PLAY.** A on an installed game asks to play it: in INSTALLED, PLAY or CANCEL; in GAMES, PLAY, INSTALL AGAIN or CANCEL. PLAY starts the folder's `default.xbe` (nxdk's `XLaunchXBE`). The app's purpose was "ready to launch from the dashboard"; launching from here saves the trip.
8. **Extracted game folders, as images.** (Added 2026-10-30: the owner's NAS holds a mixture of images and extracted folders.) A folder with a `default.xbe` in it is a game folder ([smb.md §3.1](../formats/smb.md#31-game-folders)): `@smb` lists it as one entry whose address ends in `/`. Installing it doesn't get an installer of its own: the folder's listing becomes the directory tables of a trimmed xiso held in memory, whose file bytes are read from the NAS as the installer asks ([folder-image.md](../formats/folder-image.md)). So FATX checks, the journal, resume and read-back verification are the image installer's, unchanged, and tested once. The listing's digest is the install's ETag, so a folder that changed isn't continued into; there's no image hash to compute.
9. **Archives: 7z, and folders in zips.** (Added 2026-11-01: much of the owner's collection is in `.7z`, and apps come zipped.) `.7z` is read with the LZMA SDK's 7z reader (public domain, vendored in `third_party/lzma`), with each solid block decoded here a buffer at a time ([sevenz.md](../formats/sevenz.md)): a 7z's one image streams through the sequential install like a Deflate zip member, and an archive with no image installs its game or app folder, the folder of its shallowest `default.xbe`, through the same folder image as decision 8, its files laid out in the archive's order so a solid block is decoded once ([folder-image.md §7](../formats/folder-image.md#7-archives)). Zips without an image get the same folder install, inflating each member as it's read. Supported 7z methods are Copy, LZMA, LZMA2 and LZMA(2)+BCJ; others (BCJ2, PPMd, AES) are refused by name before anything is written. The dictionary must fit in the console's free memory, measured when the install starts; one that doesn't is refused with both sizes, since 7-Zip's Ultra level (64 MiB) can't be decoded on a stock console. RAR isn't supported: its decoder's licence and size aren't worth it when 7-Zip repacks to 7z or the NAS can hold the folder.
10. **Deleting installs.** An install that isn't finished (or one that is) can be deleted from the console: in INSTALLED, A on an unfinished one, or DELETE in an installed game's PLAY question; in GAMES, DELETE in the NOT FINISHED question. Each asks again, with KEEP the default. Only a folder this app made (a marker or a journal in it) in the install folder or `E:\Apps` is deleted, recursively (`xc_nx_remove_tree`); saved games are elsewhere (`E:\UDATA`) and stay.
11. **Apps install to `E:\Apps`.** The install question offers the other folder: INSTALL / AS AN APP for a game, INSTALL / AS A GAME for an item whose path has a folder named Apps, Applications, Homebrew, Emulators or Dashboards, which then goes to `E:\Apps` by default. INSTALLED lists what this app installed in both; PLAY starts either.

## Consequences

- A NAS works as a source with nothing on a PC: install over the LAN at close to the console's 100 Mbit/s (reads are 1 MiB requests), resumable, verified, from `.iso`, `.xiso` and `.zip` images.
- The XBE grows by about 220 KB (libsmb2 and the client). No new kernel function is imported.
- LGPL-2.1: the release zip carries libsmb2's licence and says where its source and the port are; the XBE can be rebuilt from this repository with a changed libsmb2.
- An NT hash on the console's drive is a credential: anyone who can read the drive (FTP) can log in to the NAS as that user. The guide says to use a read-only NAS user for the console.
- Map loading connects to each `@smb` NAS. A NAS that's off costs 3 seconds per folder (the probe in smb.md §4), not the request timeout.
- Extracted game folders on the NAS install like images (decision 8), and so do `.7z` archives and zips of game or app folders (decision 9). Compressed CCI and CSO images, and RAR archives, aren't installed.
- A 7z made with a dictionary larger than the console's free memory can't be installed; the message says to repack it at 7-Zip's Normal level or extract it on the NAS. A 7z image's decoder state isn't saved, so a resumed install decodes the image from its start again (keeping finished files).
- The XBE grows by about 70 KB for the LZMA SDK and the archive readers. Running games straight from the NAS stays out of scope (it needs a kernel-level loader).
- A game folder costs one directory listing per folder in it before the install starts, and one open per file during it: on a LAN, a few seconds for a game of a few thousand files.
- Testing: libsmb2 and the client are tested on the PC against two SMB servers (Impacket's and a Go server): logins, guest, shares, folders, installs of every image kind and of game folders with byte-for-byte checks, a dropped connection mid-read, an install resumed after one, a folder that changed between attempts, and a NAS that's off. The console's lwIP side (the scan, the sockets under libsmb2) needs a hardware run ([testing.md](../testing.md#nas-over-smb)).
